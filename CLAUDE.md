# HelloClient — тестовое задание (headless sidebar menu)

## Контекст

Тестовое задание от компании **HelloClient** (делают CRM) для найма на позицию
frontend-разработчика. Источник задания:
https://helloclient.notion.site/HelloClient-28cc51068cd580409c8cff7e0eb65b7d
(страница на JS/Notion, WebFetch её не рендерит — текст задания получен через
скриншот от пользователя).

## Суть задания

Сделать **headless** (без стилизации) компонент бокового меню — компонент
содержит только логику, без визуала. Стили и внешний вид должны быть полностью
на стороне компонента-потребителя.

## Требования

1. **React + TypeScript + Tailwind**.
2. Логика повторяет референс-видео и макеты (узкий/широкий варианты меню).
3. Только **JSX-компонентный подход** — никаких JSON/JS-конфигов для описания
   пунктов меню (т.е. пункты меню задаются через JSX-детей/composition, а не
   через массив конфигурации).
4. Удобный API для интеграции с внешним стейтом (роутер, localStorage,
   useState) — компонент не должен диктовать, откуда берётся состояние.
5. **Настоящий headless UI**: вся логика — в headless-компоненте; стили и
   внешний вид — только в компоненте-потребителе.
6. Демонстрация гибкости — интеграция с **React Router**, но сам React Router
   **нельзя** использовать внутри headless-меню — весь роутинг только в
   компоненте-потребителе.
7. Комментарии в коде.
8. Адаптив под мобилку — меню меняет поведение при изменении вьюпорта (узкий
   ↔ широкий режим).

## Сверка с Notion: референс-видео и макеты (зафиксировано)

Полная Notion-страница открыта через Playwright MCP (`playwright` MCP-сервер),
текст требований совпадает с уже описанным выше. Ниже — детали логики меню
из референс-видео (реальный сайдбар HelloClient CRM, ~36 сек) и четырёх
статичных макетов с аннотациями (узкий/широкий, с подменю и без).

### Широкий режим (max)

- Пункт = иконка + подпись, кнопка "свернуть" — внизу колонки меню.
- Активный пункт подсвечен (светлый фон + акцентный цвет иконки/текста).
- Если у пункта есть дочерние пункты, подменю раскрывается **инлайн**, под
  самим пунктом, с отступом и буллитами (не оверлей) — рендерится в том же
  блоке колонки.
- Подменю раскрывается **по клику** на родительский пункт, либо
  **автоматически**, если активен (по роуту) один из дочерних пунктов.
- Если активен дочерний пункт — родительский пункт тоже обязан быть
  подсвечен И раскрыт.
- Аккордеон-поведение: раскрытие одного родительского пункта с подменю
  автоматически схлопывает ранее раскрытый другой пункт (открыт максимум
  один раздел одновременно) — подтверждено видео (Inventory → Clients →
  Inventory).

### Узкий режим (min/collapsed)

- Только иконки, без подписей; лого тоже схлопывается (в видео — до
  инициалов "HC").
- Активный пункт подсвечен так же, как в широком режиме.
- Кнопка "развернуть" — внизу колонки, там же где была кнопка "свернуть" в
  широком режиме (один и тот же слот, меняется иконка).
- Если у пункта есть дети — подменю показывается **flyout-попапом справа**
  от иконки: заголовок (имя родителя, жирным) + плоский список дочерних
  пунктов без иконок.
- Flyout активируется **по hover ИЛИ по клику** на родительский пункт (клик
  важен для touch/мобильных сценариев без hover).
- Активный дочерний пункт в flyout подсвечен так же, как обычный активный
  пункт.

### Мобильный/узкий вьюпорт (адаптив, отдельное референс-видео ~12 сек)

- При сужении вьюпорта сайдбар превращается в **нижний таб-бар**
  (фиксированный снизу экрана, только иконки).
- Тап по пункту с детьми открывает **bottom-sheet модалку** поверх контента
  (затемнённый фон-оверлей): заголовок с именем родителя + кнопка закрытия
  (X) + плоский список дочерних пунктов под заголовком.
- Это отдельный режим поведения от desktop-flyout — то есть логика меню как
  минимум различает три состояния вьюпорта/режима: wide / narrow(desktop) /
  mobile, а не только collapsed/expanded.

### Выводы для API (шаг 2 плана)

- Headless-хук должен уметь отличать как минимум: `variant`
  ("wide"/"narrow", контролируется потребителем/`matchMedia`) и отдельно
  mobile-brekpoint, который меняет **способ показа** подменю (inline vs
  flyout vs bottom-sheet) — сам механизм рендера подменю (Popover/Sheet)
  остаётся на стороне потребителя, headless отдаёт только состояние
  открыт/закрыт + `data-*`.
- Раскрытие подменю — accordion (single-open), не multi-expand — заложить
  в `useSidebarMenu` как поведение по умолчанию.
- Автораскрытие + подсветка родителя при активном дочернем пункте — часть
  логики хука, должна работать без завязки на конкретный роутер (потребитель
  передаёт `isActive`/current route, хук лишь синхронизирует
  expanded-состояние родителя).
- Триггер flyout/inline — и hover, и click должны быть доступны (headless
  отдаёт обработчики на оба, потребитель решает, что использовать в своей
  реализации UI).
