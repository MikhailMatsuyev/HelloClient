# Git-workflow и нейминг веток

Проект небольшой (тестовое задание, один разработчик), поэтому используем
упрощённый trunk-based подход: `main` — всегда рабочая ветка, вся разработка
идёт в короткоживущих ветках с последующим мёрджем в `main`.

## Нейминг веток

Формат: `<тип>/<краткое-описание-через-дефисы>`

| Тип        | Когда использовать                                      |
| ---------- | --------------------------------------------------------- |
| `feat/`    | Новая функциональность (например, `feat/headless-menu-core`) |
| `fix/`     | Исправление бага                                           |
| `chore/`   | Настройка тулинга, конфигов (ESLint, Husky, Vite и т.п.)   |
| `docs/`    | Документация (README, файлы в `docs/`)                     |
| `refactor/`| Рефакторинг без изменения поведения                        |

Описание — на английском, в нижнем регистре, слова через дефис, без указания
номера задачи (в этом проекте трекера задач нет).

Примеры:

- `feat/menu-compound-api`
- `feat/router-integration-demo`
- `chore/setup-tailwind`
- `docs/add-plan`

## Коммиты

Используем [Conventional Commits](https://www.conventionalcommits.org/):
`<type>: <описание>`, где `type` — `feat`, `fix`, `chore`, `docs`, `refactor`,
`style`, `test`. Пример: `feat: add Menu.Root with controlled/uncontrolled state`.

## Мёрдж

- Ветку в `main` мёрджим после того, как соответствующий шаг из
  [plan.md](plan.md) выполнен и код проверен (линт, типы, ручная проверка в
  браузере).
- Предпочтительно squash-мёрдж, чтобы история `main` оставалась линейной и
  читаемой.
