## 2. Проектирование API headless-компонента

Реализовано в `src/headless-menu/` на ветке `feat/menu-compound-api` (26 тестов, lint+typecheck
чистые). API: `Menu.Root/List/Item/Sub/SubTrigger/SubContent/Toggle`.

- [x] Выбрать паттерн composition: compound components (`Menu.Root`, `Menu.List`, `Menu.Item`,
      `Menu.Sub`/`Menu.SubTrigger`/`Menu.SubContent`, `Menu.Toggle`) на основе React Context —
      без JSON/JS-конфигов. Названия по аналогии с Radix `DropdownMenu.Sub`/`SubTrigger`.
- [x] Определить controlled/uncontrolled API для состояния (`collapsed`, `openValue` — id открытого
      раздела подменю) через общий типизированный хук `useControllableState<T>`.
- [x] Продумать, как потребитель подключит внешний стейт: `active` на `Menu.Item` — готовый булев
      проп, который считает сам потребитель (роут/localStorage/useState); `collapsed`/`openValue`
      можно и не контролировать явно, и подключить к любому внешнему источнику через
      controlled-режим. Реальная интеграция с React Router и localStorage — демо-компонент, шаг 4.
- [x] Headless-модуль не импортирует `react-router` и не содержит роутинг-логики — проверено:
      `isActive`/`active` полностью вычисляет потребитель.
- [x] `asChild`/`Slot`-паттерн реализован (`Slot.tsx`): мерж `className`/`style`/обработчиков
      (оба вызываются, не перезаписывают друг друга) и `ref` (через `mergeRefs`).
- [x] `data-state="expanded|collapsed"` на `Root`/`List`/`Toggle`, `data-state="open|closed"` на
      `Sub`/`SubContent`, `data-active` + `aria-current="page"` на активном `Item`.
- [x] Вся логика стейта — в `useSidebarMenu` (collapsed + accordion), не завязана на JSX,
      протестирована через `renderHook` без рендера DOM (`useSidebarMenu.test.ts`).
- [~] Контекст один (`SidebarMenuRootContext`), не разделён на state/actions — но его значение
  мемоизировано (`useMemo` по всем полям), так что лишний ре-рендер не возникает при
  неизменных зависимостях. Разделение на два контекста осознанно не делали (YAGNI: для
  объёма стейта этого компонента не даёт ощутимой выгоды) — пересмотреть, если в шаге 3
  появится явная просадка производительности.

### Что дополнительно проверено тестами (после ревью)

- `data-state` на самом `Root`, `List` и `Sub` (не только на `Toggle`/`SubContent`).
- Осмысленная ошибка вне обязательного родителя — для всех компонентов, которым он нужен
  (`List`, `Toggle`, `Sub` вне `Root`; `SubTrigger`/`SubContent` вне `Sub`).
- `Menu.Item` осознанно работает автономно, без `Menu.Root` — задокументировано тестом и
  комментарием в коде (ему не нужен стейт меню).
- `asChild` на `Menu.Toggle`: обработчик потребителя и переключение `collapsed` вызываются оба.
- `Slot` с невалидными children — не рендерит ничего, логирует ошибку в DEV.
- `useSidebarMenu`: controlled `closeSubmenu`, несколько переключений `collapsed` подряд.
- Попутно найден и исправлен баг тестовой инфры: RTL не чистил DOM между тестами в одном файле
  (в `vite.config.ts` нет `test.globals: true`, поэтому не сработал авто-`afterEach`-детект RTL) —
  добавлен явный `cleanup()` в `src/test/setup.ts`.

### Принципы, которые проверяем в code review

- **Composition over configuration** — нигде не должно быть `items.map()` по конфиг-массиву.
- **KISS/YAGNI** — не проектировать generic-систему на все случаи жизни; расширяемость через
  добавление новых компонентов-потомков, а не разрастающийся список пропсов на `Root`.
- **Explicit over implicit** — роутинг и `isActive` вычисляет потребитель, не headless.
- **Accessibility-first** — `nav`/`aria-label`, `aria-expanded`, `aria-current="page"`,
  `aria-controls`, клавиатурная навигация (стрелки, Home/End, Enter/Space, Escape), возврат
  фокуса на trigger при закрытии.
- **Анти-паттерны**: god-component с кучей несвязанных булевых пропсов; fetch/routing/localStorage
  внутри headless-пакета; один гигантский context на всё дерево; утечка Tailwind-классов внутрь
  headless-компонентов (grep на `className=` в `src/headless-menu` должен быть пустым, кроме
  `...rest`).

## 3. Реализация логики меню

Реализовано в `src/headless-menu/` на ветке `feat/menu-keyboard-a11y` (30 тестов, lint+typecheck
чистые). Большая часть состояния уже была сделана в шаге 2 — здесь в основном закрыли
клавиатурную доступность.

- [x] Состояние "узкий/широкий" режим (collapsed/expanded) с controlled/uncontrolled API — сделано
      в шаге 2 (`useSidebarMenu`).
- [x] Состояние активного/выбранного пункта меню — сделано в шаге 2 (`active`-проп на `Menu.Item`,
      вычисляет потребитель).
- [x] Логика раскрытия/закрытия вложенных пунктов — сделано в шаге 2 (accordion в `useSidebarMenu`).
- [x] Клавиатурная доступность и ARIA-атрибуты — **осознанно НЕ реализовывали стрелки/Home/End**,
      как было в исходной формулировке этого пункта: компонент — это `<nav>` с обычными
      кнопками/ссылками, а не ARIA-виджет `role="menu"`/`menubar`; для такой навигации Tab/Shift+Tab
      и Enter/Space уже корректно работают нативно в браузере, а свой roving-tabindex со стрелками
      сломал бы привычную Tab-навигацию по сайту и был бы избыточной генерализацией (см. принципы
      KISS/YAGNI ниже). Вместо этого сделали то, что реально соответствует паттерну ARIA Disclosure
      для `Menu.Sub`/`Menu.SubTrigger`/`Menu.SubContent`:
  - `Escape` закрывает открытое подменю и возвращает фокус на его `SubTrigger` (работает
    независимо от того, показывает ли потребитель подменю инлайн, во flyout или в bottom-sheet).
  - `aria-controls` на `SubTrigger` ⇄ `id` на `SubContent`.
  - Публичный хук `useMenuSub()` (`{ value, open, close, toggle }`) — для кастомных элементов
    управления внутри `Menu.Sub`, которым не подходит готовый `SubTrigger` (например, отдельная
    кнопка "×" в шапке мобильного bottom-sheet — см. макет в CLAUDE.md).
- [x] Адаптивное поведение — сделано в шаге 2 (`useMatchMedia`, брейкпоинт параметром).
- [x] Unit-тесты на `useSidebarMenu`/`useControllableState` — сделаны в шаге 2 (`renderHook`, без
      рендера DOM). Пункт "индексация для клавиатурной навигации" из исходной формулировки не
      применим — см. решение по стрелкам/roving tabindex выше.
- [x] Integration-тесты (RTL): `List`/`Toggle`/`Sub`/`SubTrigger`/`SubContent`/`useMenuSub` вне
      обязательного родителя кидают осмысленную ошибку; `asChild`/`Slot` мержит пропсы и форвардит
      `ref` (на примере `<a>` вместо `<button>`); Escape закрывает подменю и возвращает фокус;
      `aria-controls`/`id` связаны.

### Что дополнительно проверено/решено после ревью

- `mergeRefs` (`src/headless-menu/mergeRefs.ts`) — вынесена в отдельный файл (нужна и в `Slot`
  для `asChild`, и в `SubTrigger` для внутреннего `triggerRef`), покрыта unit-тестами отдельно
  (`mergeRefs.test.ts`): null/undefined-рефы, callback- и object-форма вместе, порядок вызова,
  очистка при размонтировании.
- Тест, что внешний `ref` потребителя на `Menu.SubTrigger` (без `asChild`) и внутренний
  `triggerRef` (нужен для возврата фокуса по Escape) действительно мержатся в один и тот же узел.
- **Явное решение по границе действия Escape** (было под вопросом на ревью): `Escape` закрывает
  открытый `Menu.Sub`, только если фокус ещё внутри ЭТОГО раздела (см. комментарий в `Sub.tsx`).
  Раздел не ловит фокус (`Tab` свободно уходит в соседние триггеры), поэтому если фокус уже
  переместился на триггер другого, закрытого `Sub`, Escape там — no-op и не закрывает открытый
  где-то ещё раздел. Это осознанный выбор (симметрично отсутствию focus-trap), а не пробел —
  зафиксирован тестом ("Escape привязан к фокусу внутри своего Sub").
- Аналогично зафиксировано комментарием в `useSidebarMenu.ts`: при переключении между разделами
  через клик/Enter/Space на другом триггере (не через Escape) фокус программно не двигаем — он
  и так уже на новом триггере, который и породил событие.
- Повторный `Escape` подряд (второй раз уже нечего закрывать) — не ломается, покрыто тестом.

## 4. Компонент-потребитель (демо)

Реализовано в `src/demo/` + `src/App.tsx` на ветке `feat/menu-demo` (73 теста, lint+typecheck
чистые). `Sidebar` (десктоп, широкий/узкий по макетам) и `MobileNav` (нижний таб-бар + bottom-sheet
на мобильном) — два независимых `Menu.Root`, переключаются между собой чистым CSS (`hidden
md:flex`/`md:hidden`), но делят один React-стейт `openValue` через пропсы (`useSidebarState`).

- [x] Стилизация через Tailwind поверх headless-компонента для обоих режимов (узкий/широкий) и
      мобильного bottom-sheet, согласно макетам и референс-видео.
- [x] Интеграция с React Router (`HashRouter` — без серверных rewrite-правил на GitHub Pages):
      `active`/`aria-current` через `useLocation()`, переходы по клику через `Menu.Item asChild` +
      `<Link>`; `useSidebarState` синхронизирует открытый раздел подменю с текущим роутом через
      "adjust state during render" (не `useEffect` — см. react.dev), включая переходы вперёд/назад.
- [x] Persist состояния: `collapsed` — в localStorage (`useLocalStorageState`), причём дефолт
      для первого визита (пока в localStorage ничего нет) берётся из `useMatchMedia` — единственное
      реальное использование этого хука в демо, до этого он был протестирован только на уровне
      headless-пакета и нигде не подключён.
- [x] Проверка адаптива вручную в браузере (Playwright MCP: ресайз до 1280×800 и 390×800) —
      узкий/широкий/мобильный режимы, flyout по hover/click, bottom-sheet, persist через reload.
- [x] Accessibility: `vitest-axe` без нарушений (Sidebar широкий/узкий, MobileNav закрыт/открыт,
      App целиком); `aria-expanded`/`aria-current`/`aria-controls` проверены явными assert'ами.

### Баги, найденные и исправленные при ручной проверке в браузере

Часть — типичные мелочи, часть (особенно 4 и 6) — по сути баги в самой логике взаимодействия,
не просто визуальные огрехи:

1. Иконки пунктов меню рендерились 0×0 (`<svg>` без `width`/`height` и без Tailwind-класса в
   местах использования) — дефолтные `width={20} height={20}` в `icons.tsx`.
2. В узком режиме `SubTrigger` иногда оставался без доступного имени для скринридера — `title`.
3. Горизонтальный скролл в узком сайдбаре: `Menu.List` был `overflow-y-auto`, а flyout
   (`position: absolute`) считается в scroll-область — по CSS-спеке `overflow-x: visible` рядом с
   `overflow-y: auto` принудительно становится `auto`. Убрали `overflow-y-auto` (пунктов мало).
4. Два flyout видны одновременно (клик открыл Inventory, наведение на Clients показывало оба
   сразу) — hover был чистым CSS (`group-hover`), не знал про accordion-стейт. Теперь hover идёт
   через `useMenuSub().openThis` (тот же accordion-экшен, что и клик).
5. Раздел с активной страницей внутри терял синюю подсветку, стоило навести на соседний, —
   добавлен отдельный персистентный `data-active` (не зависит от временного `data-state=open`).
6. **Реальная гонка событий**: в узком режиме `Menu.SubTrigger` совмещал `onClick` (встроенный
   `toggleSubmenu`) и `onMouseEnter` (`openThis`) на одном элементе — мышь всегда сначала входит
   в элемент (hover открывает), затем кликает (toggle тут же закрывает открытое hover'ом).
   Исправлено полным отказом от `Menu.SubTrigger` в пользу кастомной кнопки на `useMenuSub()`,
   где в узком режиме и hover, и click вызывают только `openThis` (не toggle).
7. Flyout, открытый по hover, не закрывался, если увести курсор в сторону (не на соседний
   `SubTrigger`) — не было `onMouseLeave` вообще. Добавлен на весь `Menu.Sub` (не на триггер:
   `mouseleave` не всплывает и не сработает, пока курсор двигается с триггера на сам flyout —
   тот DOM-потомок `Menu.Sub`, хоть и абсолютно спозиционирован визуально в стороне).

Находки 4, 6, 7 дошли до продакшен-кода именно благодаря пошаговой ручной проверке в реальном
браузере (Playwright MCP) вперемешку с ревью от второй модели (Fable) — юнит/интеграционные тесты
такие вещи, завязанные на реальный порядок DOM-событий и визуальное поведение, не ловят сами
по себе без явного теста на конкретный сценарий (который для 4, 6, 7 был дописан постфактум).
